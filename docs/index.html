Open the system menu, click the Remmina tile, pick a saved connection. The list is read from Remmina’s own profile directory and follows it as it changes, so a connection saved in Remmina appears here without a reload and without the extension being restarted.

Profiles

A Remmina profile is a .remmina file: GKeyFile with a single [remmina] section of flat key=value lines. QuickRem reads five of those keys — name, group, protocol, server and username — and ignores the rest. Profiles are listed by name, collated the way the reader’s locale collates, and a file with no usable name falls back to its filename stem.

Each entry carries an icon chosen from its protocol:

Protocol Icon
SSH utilities-terminal-symbolic
SFTP folder-remote-symbolic
RDP, VNC, GVNC, SPICE preferences-desktop-remote-desktop-symbolic
WWW web-browser-symbolic
EXEC system-run-symbolic
anything else network-server-symbolic

The directory is found rather than configured. Highest precedence first: the profile-dir setting, then datadir_path from remmina.pref, then a native install’s $XDG_DATA_HOME/remmina, then the Flatpak’s ~/.var/app/org.remmina.Remmina/data/remmina. A native install wins over the Flatpak because its profiles are the ones remmina -c on the command line would open.

A fresh Remmina install has no profile directory at all. QuickRem watches the nearest ancestor that does exist and moves the watch onto the real directory once it appears, so the list fills in on its own rather than needing the extension turned off and on again.

Install

Needs GNOME 49 or newer, and Remmina. From the latest release, with no clone and no toolchain — gnome-extensions ships with GNOME Shell itself: 

curl -LO 'https://github.com/napalm255/quickrem/releases/latest/download/quickrem@napalm255.github.io.shell-extension.zip'
gnome-extensions install --force 'quickrem@napalm255.github.io.shell-extension.zip'

That unpacks the extension and compiles its settings schema, so there is no separate glib-compile-schemas step. Log out and back in — Wayland cannot reload the Shell in place — then turn it on: 

gnome-extensions enable quickrem@napalm255.github.io

From a clone:

just setup
just install
just enable

A brand-new extension is invisible to a running Shell on Wayland, so the first just enable after a fresh just install reports that the extension does not exist. Log out and back in, then run it.

Preferences

just prefs, or the Settings entry at the bottom of the menu. The first row shows which directory QuickRem resolved and how it got there, so a wrong guess is visible rather than silent — including when the directory does not exist yet.

Setting Leaving it empty means
Profile directory Detect it: datadir_path, then a native install, then the Flatpak
Launch command Use the application registered for application/x-remmina

Launch command is the escape hatch for an unusual install. It is split with GLib.shell_parse_argv and the profile path is appended as a separate argument, never interpolated into the string.

Launching

Remmina exposes no D-Bus interface and is not D-Bus activatable, so something has to be executed. The obvious choice — shelling out to flatpak run org.remmina.Remmina -c <path> — is the wrong one: it hard-codes the packaging, and a path handed straight to a sandboxed process is not necessarily a path that process can see.

Instead QuickRem opens a profile through whatever is registered for application/x-remmina. On a Flatpak install that resolves to Remmina’s own connect entry: 

Exec=flatpak run --command=remmina-file-wrapper --file-forwarding \
     org.remmina.Remmina -c @@u %U @@

That entry is the -c connect action, and --file-forwarding makes the portal translate the path into the sandbox. The same call works unchanged against a distribution package, reuses an already-running Remmina through GApplication, and needs no branching on how Remmina was installed. Opening Remmina’s own window goes through Shell.AppSystem, which brings its own launch context so the window lands on the workspace the click came from.

Secrets

Remmina encrypts stored passwords with a key kept in remmina.pref. QuickRem cannot decrypt them and does not try. modules/profiles.js drops every key matching password, passphrase or secret while parsing, rather than filtering them out later — so a future code path that forgets to filter has nothing to leak into a menu label, a subtitle or the journal.

remmina.pref itself is read for exactly one key, datadir_path. The secret= sitting beside it is never returned and never kept.

Both claims are tested. A unit test asserts the parsed object contains none of the ciphertext and has only the six expected keys, and the live check greps a whole Shell session log for a fixture password and requires zero occurrences.

Architecture

File Imports Job
extension.js Shell Pair construction with teardown, nothing else
modules/profiles.js nothing Parse a profile, sort, map protocol to icon
modules/paths.js nothing Decide which directory to read
modules/store.js Gio, GLib, GObject Scan and watch it; publish profiles
modules/launch.js Gio, GLib, Shell Decide what to run, and with which arguments
modules/panel.js St, QuickSettings The tile, its menu and its rows
prefs.js Adw, Gtk Preferences, in its own process

The store owns the data and the panel owns the widgets. The panel rebuilds from notify::profiles and holds no profile state of its own, so there is one place where the list can be wrong.

Scanning is asynchronous throughout. A profile directory lives on whatever the home directory is mounted from, and a synchronous read blocks the compositor thread — a stutter in the whole desktop, not just in this menu. File events are debounced, because Remmina rewrites a profile in several steps when it saves, and a generation counter throws away a scan that a newer one has overtaken.

Why the list scrolls

QuickToggleMenu has no scrolling of its own. Measured on a 1080p screen, thirty profiles want 1296px of a 1048px work area and the surplus is simply clipped. GNOME’s own Wi-Fi menu answers this by showing eight networks and sending you to Settings for the rest, which suits a list you skim but not one you pick from: the point here is that any saved connection is one click away.

So modules/panel.js subclasses PopupMenuSection and swaps its actor for an St.ScrollView around the same box. PopupMenuBase.addMenuItem() adds section.actor but does its bookkeeping against the section object, so key navigation, open-state propagation and activation all survive the swap. The cap is half the work area, recomputed on every rebuild and every menu open — which picks up a monitor change or a text-scaling change without watching for either. Below the cap no scrollbar appears at all.

Testing

modules/profiles.js and modules/paths.js import nothing — not gi://, not resource:/// — so Vitest runs them on plain Node exactly as they ship. modules/store.js runs against an in-memory Gio in tests/stubs/, which is what makes the debounce, the generation counter and the watch re-attach reachable from a unit test at all. Timeouts are queued rather than scheduled, so “this burst of five events caused one rescan” is a direct assertion rather than a sleep.

modules/launch.js is split out so the launch path can be tested at all: panel.js imports St and QuickSettings, which a unit test cannot supply meaningfully, and the launch code carries this extension's one security invariant — a profile path is its own argument-vector element and is never interpolated into launch-command, so a profile named with a semicolon is an argument rather than a second command. A test fails if that stops being true.

prefs.js is tested too, mostly to pin one trap: _() may not be called while a module is being evaluated. A translated string in a module-level table throws gettext can only be called from extensions and the preferences window then never opens — silently, because nothing else in the extension imports prefs.js. The stub’s gettext throws unless a test says otherwise, so importing the module is itself the check.

modules/panel.js and extension.js are widget construction and lifecycle wiring. Asserting those against stubs of the toolkit tests the stubs, so they are covered by scripts/headless-check.sh instead, which boots a throwaway headless gnome-shell in isolated XDG directories, enables, disables and re-enables the extension, plants and removes a profile while it runs, and fails on a JavaScript error, a leaked signal handler or a deallocated-object warning. The enable/disable/enable cycle is the point: a connect that outlives its disconnect only shows up on the second enable.

Packaging

just build makes the zip with plain zip, because gnome-extensions ships inside the gnome-shell package and CI has no GNOME — making the build depend on it would pull a whole desktop onto every runner. The cost is that nothing checks the archive layout, and extensions.gnome.org is strict about it, so scripts/pack-check.sh keeps the official tool as the authority and diffs the two archives, then asserts metadata.json sits at the archive root.

Contributing

main is protected: no direct pushes, no force-pushes and no merge commits. Everything lands through a pull request whose title is a Conventional Commit — that title becomes the squashed commit subject, so the convention survives the merge. 

git switch -c type/short-description
just ci
gh pr create --fill
gh pr merge --squash --auto

ci and CodeQL have to pass before the merge button unlocks, and the branch has to be current with main. No approving review is required, so a single maintainer is not locked out of their own repository.

Releasing

Set the version in metadata.json and package.json and land that through a pull request like anything else. Then tag the merged commit and push the tag — tags are not covered by branch protection: 

git switch main && git pull
git tag -a v0.1.0 -m 'release v0.1.0'
git push origin v0.1.0

The release workflow checks the tag against both files before it builds anything. A tag that disagrees with the tree would otherwise ship a release titled v0.2.0 containing a zip that tells GNOME it is 0.1.0, and nothing downstream would notice. The full suite gates the publish.

Development

just            # list every recipe
just test       # unit suite, runs on Node
just lint       # eslint, prettier, gschema and shellcheck
just security   # gitleaks, trivy, osv-scanner, actionlint, zizmor
just ci         # everything CI runs
just fixtures 5 # throwaway profiles, to exercise the menu and the watcher
just test-live  # headless Shell smoke test, then the packer check
just logs       # follow the extension's output
just clean      # remove node_modules, coverage and build output

mise.toml pins every tool, so just ci behaves the same locally and on a runner. gjs, glib-compile-schemas, gnome-shell and gnome-extensions come from the system rather than mise, because they have to match the Shell you are targeting.
